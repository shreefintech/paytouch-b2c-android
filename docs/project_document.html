1. Project Overview

PayTouch Consumer is a utility bill payment and digital wallet app for Indian consumers. It centralises electricity, gas, mobile, DTH, cable, broadband, FASTag, loan, and municipal tax payments into a single app with a shared wallet, unified transaction history, and consistent payment receipts. Built by Shree Fintech Solutions and powered by the PayTouch platform (paytouch.in).

Current state: UI implementation phase. All network calls are stubbed with TODO(PAYTOUCH-xxx): comments. API wiring and business logic finalization happen in a later phase.

Who Uses It

Regular consumers only — single user role. Every logged-in user has the same feature set. Before accessing payment features, users must complete a mandatory 4-step onboarding:

  1. Register an account
  2. Complete KYC (Know Your Customer) verification
  3. Create a 4-digit MPIN
  4. Set up a Virtual Account (banking details)

  • Adapters MUST end in Adp — never Adapter

5. Architecture Rules

  • ApiClient is the only source for Retrofit — never construct Retrofit directly inside a ViewModel or Activity.
  • SharedPreferenceHelper is the only way to read/write SharedPreferences — never call getSharedPreferences() directly.
  • Constant.kt is where all hardcoded URLs and keys live — no inline strings in code.
  • ToastUtil is the only way to show user messages — never use raw Toast.makeText().
  • Utility.isInternetAvailable() must be called before every network request.
  • All Activities must extend BaseActivity — never extend AppCompatActivity directly.
  • Network errors must be parsed via ApiHelper.parseErrorMessage().
  • Adapters must not contain business logic or network calls.
  • ViewModels must not store Activity/Context references.
  • All API endpoints must be declared in ApiService or ApiAdminService — never raw HTTP calls inside Activity/ViewModel.
  • mapToTransactionItem() must use item.id?.toString() ?: "--" for userId — never loop index.
  • Never generate transaction_id client-side for payment requests — the backend owns this.
  • ViewModel base class is role-based: main payment VMs → BaseBillViewModel; report/status/receipt VMs → AndroidViewModel.
  • isMobileCategory flag must be set in every mapToTransactionItem() and mapToDisplayItem().
  • Always use Utility.maskNumber() for account numbers shown in transaction list rows.
  • Utility.formatAmount(raw: String?) for String DTOs; formatAmount(raw: Double?) for Electricity DTOs — never raw string templates.
  • Utility.formatDate() is the only date formatter — never call SimpleDateFormat directly in a ViewModel.

6. Key Code Patterns

Network Call Pattern

All Retrofit endpoints return Call<T> — never suspend fun. Always invoke with .enqueue().

// ApiService declaration
fun someEndpoint(@Field("x") x: String): Call<SomeItem>

// ViewModel call
if (!Utility.isInternetAvailable(mActivity)) return
ApiClient.apiService.someEndpoint(body).enqueue(object : Callback<SomeItem> {
    override fun onResponse(call: Call<SomeItem>, response: Response<SomeItem>) {
        if (response.isSuccessful) { /* handle */ }
        else { ToastUtil.show(mActivity, ApiHelper.parseErrorMessage(...)) }
    }
    override fun onFailure(call: Call<SomeItem>, t: Throwable) {
        ToastUtil.show(mActivity, t.localizedMessage)
    }
})

Button Loading State Pattern

Every button that triggers an API call shows a ProgressBar inside itself while the call is in flight.

// XML — DataBinding variables in <data> block
<variable name="showProgressFetch" type="androidx.databinding.ObservableBoolean" />

// Button XML — toggle label/progress
<TextView android:visibility="@{showProgressFetch ? View.GONE : View.VISIBLE}" />
<ProgressBar android:visibility="@{showProgressFetch ? View.VISIBLE : View.GONE}" />

// Kotlin — declare, assign, toggle
private val showProgressFetch = ObservableBoolean(false)
binding.showProgressFetch = showProgressFetch

showProgressFetch.set(true)   // before API call
showProgressFetch.set(false)  // in both onResponse and onFailure

// Click guard
if (showProgressFetch.get()) return@OnClickListener

Click Handling Pattern

One centralized onClickListener() with a when block. Always guard rapid taps with Utility.stopClick().

private fun onClickListener(): View.OnClickListener {
    return View.OnClickListener {
        when (it) {
            binding.btnFetch -> {
                if (Utility.stopClick()) return@OnClickListener
                onFetchBill()
            }
            binding.btnPay -> {
                if (Utility.stopClick()) return@OnClickListener
                onPay()
            }
        }
    }
}

Intent Data Passing (Object Transfer Rule)

Always pass a single object as a JSON string — never individual putExtra fields.

// Companion object in receiving Activity
private const val EXTRA_ITEM = "extra_item"

fun start(context: Context, item: MyItem) {
    context.startActivity(Intent(context, MyDetailActivity::class.java).apply {
        putExtra(EXTRA_ITEM, Gson().toJson(item))
    })
}

// Lazy field in receiving Activity
private val myItem: MyItem? by lazy {
    intent.getStringExtra(EXTRA_ITEM)?.let { Gson().fromJson(it, MyItem::class.java) }
}

Bottom Sheet Pattern

Always use BottomSheetBehavior embedded in the layout — never Dialog.

// Activity layout: CoordinatorLayout → main content + viewBg overlay + include sheet
// Sheet XML root: ConstraintLayout with app:layout_behavior="...BottomSheetBehavior"

private lateinit var sheetBehavior: BottomSheetBehavior<View>

private fun setupSheet() {
    sheetBehavior = BottomSheetBehavior.from(binding.incSheet.root)
    sheetBehavior.state = BottomSheetBehavior.STATE_HIDDEN
    sheetBehavior.addBottomSheetCallback(object : BottomSheetBehavior.BottomSheetCallback() {
        override fun onStateChanged(bottomSheet: View, newState: Int) {
            when (newState) {
                STATE_EXPANDED -> binding.viewBg.visibility = View.VISIBLE
                STATE_HIDDEN   -> binding.viewBg.visibility = View.GONE
            }
        }
        override fun onSlide(bottomSheet: View, slideOffset: Float) {}
    })
}

API Response Wrapper Rules

Response ShapeDeclarationSuccess Check
General<T> wrapped — {"data": ..., "success": ...}Call<General<YourItem?>>isSuccessful && body?.data != null
Flat — has success: Boolean fieldCall<YourItem>isSuccessful && body?.success == true
Flat — no success fieldCall<YourItem>response.isSuccessful

DTO Nullability Rule: Every field in an API response DTO must be nullable (?). Gson silently sets any missing field to null — non-nullable fields crash at runtime. Local DTOs (passed between Activities) follow normal nullability rules.

// API response DTO — all fields nullable + @field:SerializedName required
data class SomeItem(
    @field:SerializedName("id")     val id: Int?,
    @field:SerializedName("amount") val amount: Double?,
    @field:SerializedName("name")   val name: String?
)

// Local DTO — no annotations; nullable only where genuinely optional
data class SomeLocalItem(
    val id: Int,
    val amount: Double,
    val note: String?    // genuinely optional
)

Navigation Rules

  • Back stack after login: Stack is cleared — user cannot press Back to reach login from Home.
  • Forced logout (401): Stack completely cleared with FLAG_ACTIVITY_NEW_TASK or FLAG_ACTIVITY_CLEAR_TASK.
  • No cross-module navigation: Never start one module's Activity from another. Leave empty with a TODO(ticket) comment for pending modules.
  • Result refresh: Use ActivityResultLauncher when a child screen's data changes should trigger a parent refresh.
  • Object passing: Always Gson().toJson(item) into a single putExtra — never multiple individual extras.

Standard Bill Payment Flow

  1. User selects operator from API-fetched dropdown
  2. User enters consumer/account number
  3. App calls fetch-bill API → displays outstanding amount, due date, consumer name
  4. User confirms; platform fee is calculated and shown
  5. Payment processed via process-payment API
  6. App calls transaction-status for final result
  7. Success/failure sound plays (payment_success.mp3 / payment_failed.mp3)
  8. Receipt is displayed

12. DOs & DON'Ts

Architecture — DOs

  • Use ApiClient as the only Retrofit source — one client per distinct base URL
  • Use SharedPreferenceHelper as the ONLY SharedPreferences access point
  • Put all URLs, keys, and constants in Constant.kt
  • Call Utility.isInternetAvailable() before every network request
  • Handle 401 responses globally via an OkHttp interceptor — not per-ViewModel
  • Use ActivityResultLauncher for all Activity results and file picking
  • Prefer Data Binding (android:onClickListener="@{onClickListener}") over programmatic setOnClickListener()
  • Store every payment attempt in Room DB immediately — success or failure
  • Play audio feedback after every payment
  • Use MaterialCardView for card/container backgrounds — never create new drawables for solid-color shapes

Architecture — DON'Ts

  • Don't put network calls in Activities — all calls go in ViewModels
  • Don't use suspend fun or coroutines for Retrofit API calls
  • Don't create multiple SharedPreferences stores for the same user
  • Don't hardcode any active URL, key, or token in Activity/ViewModel code
  • Don't store Activity/Context references as ViewModel fields
  • Don't call Toast.makeText() directly — always use ToastUtil
  • Don't call notifyDataSetChanged() for a single-item RecyclerView update
  • Don't load images with Glide without a placeholder and error drawable
  • Don't use startActivity() without calling Utility.stopClick() first
  • Don't navigate cross-module (e.g. starting ElectricityActivity from GasActivity)

UI Loading — DON'T use full-screen loaders

Wrong: Full-screen progress dialog, overlay, or alpha-only dimming for button-triggered API calls.

Right: Show a ProgressBar inside the specific button that was tapped. For dropdown loading, show a spinner inside the field slot only. One ObservableBoolean per button — never a single shared isLoading flag.

13. Known Issues to Resolve Before Release

Issue 1 — QR Payment URL

The Dynamic QR payment feature uses a ngrok-free.dev tunnel URL which will break in production. Replace with a stable production URL before any live deployment.

Issue 2 — Static Shreefintech Token

The dynamic token from api/shreefintech-token is stored in a static field Constant.TOKEN — race condition risk in multi-thread scenarios. Move to SharedPreferenceHelper or a Repository before the API wiring phase.

Issue 3 — Legacy MobiKwik API

Some payment flows may route through dashboard.shreefintechsolutions.com/api/mobikwik/. Audit each endpoint before wiring — determine which are still active and which have been replaced by paytouch.in equivalents.

Issue 4 — Postpaid Plan Selection (B2C-59)

PostpaidActivity.onBrowsePlan() currently launches PrepaidPlanSelectionActivity as a temporary stand-in. Replace with dedicated PostpaidPlanSelectionActivity once mobile-postpaid/plans API is ready. Marked with TODO(B2C-59).
